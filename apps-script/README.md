## Borrado remoto del historial: actualización 2026-10-31

La misma implementación API se actualizó a **versión 2**, sin cambiar el ID ni ampliar los permisos o el acceso «Solo yo». `prepareHistoryClear` solo prepara una vista previa, exige propietario y devuelve un ticket de cinco minutos ligado a la cuenta, generación y secuencia del diario. No borra filas. `clearHistory` exige ese ticket, la confirmación `BORRAR HISTORIAL` y que el diario no haya cambiado desde la vista previa. Los reintentos del mismo ticket devuelven la confirmación previa sin borrar capturas posteriores.

Bajo el bloqueo del script se cambia la generación del historial antes de eliminar físicamente, de abajo hacia arriba, únicamente las filas `record`. No se renumeran ni alteran las filas de favoritos/direcciones. La secuencia tiene un mínimo persistente para no reutilizar números cuando desaparece la última fila. Si se interrumpe la operación confirmada, una llamada posterior completa la eliminación pendiente; no se amplía una operación ya confirmada para borrar registros nuevos.

Los clientes actualizados envían `clientVersion:2` y `historyEpoch`. Un cambio de generación rebobina el cursor, retira registros anteriores y descarta sus operaciones pendientes. Se preservan capturas pendientes posteriores al corte; los IDs conocidos como previamente sincronizados se retiran aunque el reloj del dispositivo hubiera asignado una fecha futura. Los clientes antiguos no pueden leer/subir después del primer borrado y deben recargar. El servidor rechaza reintroducir automáticamente capturas anteriores al último corte. Los favoritos y direcciones anteriores continúan sincronizándose.

Antes de reflejar un borrado se conserva una copia del estado local en `gpsHistoryBeforeClearV1:<generación>`; `gpsHistoryLastBackupV1` permite descargarla desde la UI. No se sobrescribe `gpsSyncBackupV1` ni las copias anteriores. El botón no borra revisiones administradas por Google Sheets ni archivos JSON descargados.

## Estructura y política de datos

`control_gps_eventos_v1` es un diario de versiones que se anexa durante la sincronización; el único borrado físico admitido es la eliminación expresa del historial GPS descrita arriba. No es una tabla para ordenar o editar manualmente. Columnas: secuencia, ID de operación, ID de entidad, tipo, revisión base, fecha/hora ISO UTC de recepción, usuario autenticado, dispositivo, datos JSON y conflicto. No ordenar, borrar ni insertar filas manualmente; utilizar el botón autorizado para borrar el historial.

- Tipos: `record`, `favorite`, `address` y, tras actualizar el backend, `name`. IDs lógicos deterministas por timestamp/coordenadas o coordenadas redondeadas a seis decimales. IDs de operación UUID estables al reintentar.
- Los registros incluyen timestamp en milisegundos, latitud, longitud y precisión en metros; fecha y hora de captura se derivan de timestamp en la zona elegida. Las direcciones incluyen fuente, calidad, país, departamento, ciudad, calle y número solo cuando existen. No hay credenciales dentro de los datos JSON.
- Una entidad puede tener varias filas/versiones. En el historial visible se fusiona por ID lógico; reintentar una operación no añade filas duplicadas. La secuencia del servidor define el orden sin confiar en relojes de los dispositivos.
- Conflicto: prevalece la última versión recibida por el servidor. La versión anterior permanece en el diario; el conflicto se marca y se informa en el cliente. Las versiones anteriores se conservan, salvo las filas de historial GPS retiradas mediante el borrado remoto expreso. Un cambio local pendiente se protege mientras se descarga el remoto y después se sube como una nueva versión.
- Quitar un favorito o vaciar una dirección crea una versión desactivada/vacía. El historial GPS se conserva remotamente: borrarlo en la interfaz solo lo borra de ese navegador y puede recuperarse al reconectar. Borrar todo pausa la sincronización antes de modificar los datos locales.
- El borrado remoto masivo solo afecta al historial GPS y exige propietario, vista previa y doble confirmación. No hay retención con borrado automático. Al superar 50.000 eventos el servicio pide archivar y detiene nuevas operaciones, preservando la información.
- Primera conexión: copia íntegra local en `gpsSyncBackupV1` antes de aplicar datos remotos; la descarga de esa copia omite la clave Geoapify y la URL CSV. La cola y el cursor se guardan en `gpsSyncStateV1`. No limpiar claves del navegador si hay pendientes.
- El origen local `gpsTrackerState` se mantiene. Los JSON/CSV anteriores siguen importándose. El token OAuth nunca se guarda en localStorage, archivos, URLs o exportaciones.
- Una sola pestaña puede sincronizar mediante Web Locks. Un cambio de almacenamiento desde otra pestaña detiene la conexión para exigir recarga. Cambiar de cuenta/destino con una cola existente se rechaza; utilizar otro perfil evita mezclar historiales.

## Conexiones intermitentes y direcciones

Subidas de hasta 50 operaciones, descargas de hasta 200 eventos por página. Confirmación explícita del servidor, cursor persistido después de guardar localmente, reintentos exponenciales con variación entre unos segundos y cinco minutos. Si la respuesta se pierde tras escribir, se reenvían los mismos IDs. Errores de permisos o configuración detienen la sesión; errores de red conservan la cola. Con el transporte OAuth activo, los tokens vencidos requieren una nueva acción del usuario. El transporte de sesión nativa preparado arriba continúa pendiente de activación y prueba real; no se guarda ningún refresh token.

**Buscar dirección** utiliza Google cuando existe sesión autorizada, con confirmación para el punto. Sin sesión ofrece edición manual y conexión con Google; no utiliza Geoapify. La casilla de dirección automática autoriza únicamente nuevas capturas, nunca una consulta masiva del historial; máximo una por minuto y 20 por sesión de página. El servidor exige además `GPS_GEOCODE_ENABLED` y aplica su presupuesto compartido diario. Si hay solo administración y no calle, la dirección se etiqueta `Zona aproximada`; los campos faltantes permanecen vacíos. Se conserva la corrección manual y no se sobrescribe una corrección hecha mientras llega una respuesta. No se garantiza portal exacto, número ni apartamento.

No se configura una API de Maps con facturación ni se publican claves. Maps de Apps Script tiene cuotas de Google sujetas a cambios; revisar el consumo de la cuenta y mantener el límite de la aplicación por debajo de su cuota efectiva. No se activa envío continuo cuando la página está cerrada o suspendida.

## Verificación

Ejecutar desde el repositorio:

```bash
node --test tests/sync.test.cjs
```

La suite comprueba permisos, guardado/lectura, dos clientes, respuesta perdida después de escritura, deduplicación, conflictos, favoritos, direcciones, desconexión, cuota, paginación, bloqueo entre destinos, almacenamiento local fallido y preservación exacta del CSS anterior.

Antes de dar por activa la conexión realizar en la hoja de ensayo: OAuth desde el origen público; aceptar/rechazar permisos; escritura/lectura desde dos navegadores; recarga y reintento tras desconexión; cambios simultáneos; revocación; cuota real; validación de direcciones con coordenadas públicas de prueba. Comparar el número de IDs lógicos del backup antes/después y conservar el diario. **Las pruebas del backend y de OAuth/transporte desde Pages figuran arriba. La sincronización con dispositivos independientes y los casos reales aún no ensayados permanecen pendientes.**
